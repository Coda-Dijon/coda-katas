## 6. Cycle de vie Transient : ça va mieux, mais...

### L'exercice
1. Repassez `OrderRepository` en **Transient** dans le câblage (une nouvelle instance à chaque `resolve` — c'est déjà le comportement par défaut de votre conteneur depuis l'étape 4, il suffit de ne plus utiliser `registerSingleton` pour ce type).
2. Relancez `PizzaOrderConcurrencyTest`. Le temps total a-t-il baissé ? Pourquoi, concrètement, à la lumière du code de `InMemoryOrderRepository` ?

### Un nouveau problème à discuter
Un repository en mémoire, une fois qu'il est Transient, pose une question amusante : si chaque commande obtient sa **propre** instance de `InMemoryOrderRepository`, où vont réellement les commandes sauvegardées ? Que se passerait-il si vous appeliez `findAll()` juste après un `save()`, sur une nouvelle instance résolue séparément ?

Plus généralement, imaginez que `placeOrder` ait besoin d'appeler le repository **plusieurs fois** dans une même opération (par exemple : sauver la commande, puis incrémenter un compteur de stock). Avec un cycle de vie Transient, chaque appel à `resolve(OrderRepository.class)` renverrait une instance **différente** — on perdrait la cohérence d'une même "unité de travail" (deux connexions différentes à une base de données réelle ne voient pas forcément les mêmes écritures non encore validées).

### L'exercice (optionnel, pour bien sentir le problème)
Ajoutez une méthode `countOrders()` à `OrderRepository` / `InMemoryOrderRepository`, appelez-la juste après `save()` dans `placeOrder`, et affichez le résultat dans un log. Avec du Transient, que constatez-vous ?

### Critère de sortie
Vous pouvez expliquer, avec cet exemple concret, pourquoi **ni** Singleton **ni** Transient n'est le bon choix par défaut pour ce genre de ressource — et pourquoi la réponse dépend de ce qu'on veut partager, et à quelle échelle.
