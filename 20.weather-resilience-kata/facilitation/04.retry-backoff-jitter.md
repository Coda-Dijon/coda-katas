## 4. Backoff exponentiel et jitter : retenter intelligemment

### Le problème du retry immédiat
Votre `RetryingWeatherApi` actuel retente sans doute immédiatement, ou avec un délai fixe. Deux soucis en conditions réelles :
- Si le service en face est déjà en difficulté (surcharge), le marteler immédiatement avec des retries ne fait qu'aggraver la situation.
- Si de nombreux clients retentent tous **au même instant** avec le même délai fixe, ils créent des vagues de trafic synchronisées ("retry storm") qui peuvent elles-mêmes provoquer une panne.

### Les deux idées à combiner
- **Backoff exponentiel** : augmenter le délai entre chaque tentative (ex. 100ms, puis 200ms, puis 400ms, puis 800ms...), pour laisser de plus en plus de temps à la dépendance de récupérer.
- **Jitter** : ajouter une part d'aléa à ce délai (ex. ±20%), pour désynchroniser les clients entre eux et éviter les vagues de trafic groupées.

### L'exercice
1. Injectez un `Sleeper` dans `RetryingWeatherApi` (une interface `void sleep(Duration duration)`, avec une implémentation réelle basée sur `Thread.sleep`, déjà fournie dans le code de départ).
2. Entre deux tentatives, appelez `sleeper.sleep(...)` avec un délai calculé selon la stratégie backoff + jitter, plutôt que de retenter immédiatement.
3. Pour tester cette logique **sans ralentir votre suite de tests** (et sans flakiness liée à l'aléa), injectez un `Sleeper` de test qui n'attend pas réellement, mais qui **enregistre** les durées demandées. Vos tests peuvent alors vérifier que les délais suivent bien une progression croissante (avec une tolérance pour le jitter), sans jamais réellement attendre.

### Discussion
Pourquoi est-ce important d'injecter le `Sleeper` plutôt que d'appeler `Thread.sleep` directement dans `RetryingWeatherApi` ? Faites le lien avec ce que vous avez appris sur l'injection de dépendances dans le kata Pizzeria.

### Critère de sortie
- Un test qui prouve la progression du délai entre tentatives (croissant, jamais deux fois exactement le même en présence de jitter).
- Votre suite de tests reste rapide (quelques millisecondes, pas plusieurs secondes) malgré le retry avec backoff.
